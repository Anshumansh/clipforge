## What actually needs grandfathering right now

The 12 existing accounts are all on the legacy Free plan: **50 credits, refilled
implicitly** (there's no expiry/rollover logic today — `User.credits` is a running
balance topped up on plan changes and admin actions). The new Free plan is **20
credits, granted once on email verification, not recurring.**

If the new Free definition were applied retroactively to these 12 accounts, every one
of them would see their standing terms reduced without asking for it — precisely
what the brief prohibits ("Do not unexpectedly change existing customers").

**Grandfathering mechanism (already built, not yet activated):**
- `User.planVersionId` is `null` for all 12 existing accounts, and stays that way
  through this entire pricing overhaul unless explicitly changed.
- Every place that will eventually check "what plan is this user really on" is
  required to treat `planVersionId: null` as "resolve through the legacy
  `lib/plans.ts` definitions, not the new `PLAN_CONFIGS`" — `lib/pricing/plan-versions.ts`'s
  `resolvePlanConfig(null)` already returns `null` specifically so callers can't
  accidentally fall through to the new config for a legacy account.
- No code path in this overhaul writes to `planVersionId` for an existing user. The
  only way an existing account moves onto the new structure is a future, explicit,
  owner-approved migration step — not automatic, not a side effect of deploying this
  work.

**What this table cannot show yet:** real cost-side margin per account. That requires
`JobCostRecord` data (section 6), which isn't populated by any live job runner in
this pass — wiring cost capture into the actual render pipeline was deliberately
scoped out of this pass so it could be reviewed on its own. Until that exists,
`lossMakingAccountIds` in the report is always empty — not because nothing is
loss-making, but because there's no data to check yet. Do not read the empty list as
"nothing is unprofitable."

## Migration schedule

No schedule exists. Given zero paying customers, there is no urgency driving one —
the practical next step is:
1. Wire `recordJobUsage` into the three job runners (script/repurpose/ugc) so real
   cost data starts accumulating.
2. Let it run long enough to see real per-plan contribution margins (the brief's own
   stage 6: "Monitor real costs and margins for 30 days").
3. Re-run `generateMigrationImpactReport()` with real cost data behind it.
4. Owner reviews the real numbers and decides whether/when to open the new plans to
   new signups (stage 5), and separately whether/when to offer existing free accounts
   the option to move to the new structure.

## Approval gate

Per the brief (section 11 and section 13): **do not send this notice, do not assign
any existing account a `planVersionId`, and do not change any existing account's plan
terms without explicit owner sign-off**, given in writing (e.g. approving this
document, or a specific follow-up instruction). Nothing in this pricing overhaul pass
does any of those three things on its own.
